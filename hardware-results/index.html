    v2 vs v3 on ROCm (same conditions)¶

    The first row is the v2 baseline from the morning. In the afternoon both versions measured ~6% slower at c=1, so the v2/v3 comparison was re-run back to back: v2 code (commit 5910c31) and v3 each served from a fresh start, then clef bench --concurrency 1,4,8,16 --requests 100. v3 also ran 300-request c=1 runs: p50 148.0-150.3 ms, the same as v2's 149.1-149.3 ms in the same window.

    conc v2 req/s v3 req/s (run 1 / run 2) v2 p50 ms v3 p50 ms
    1 6.6 6.6 / 6.7 150.1 149.0 / 149.3
    4 7.2 7.0 / 7.0 547.9 566.3 / 569.3
    8 8.3 8.2 / 8.1 945.2 956.5 / 965.7
    16 8.1 8.8 / 8.9 1766.5 1746.5 / 1754.3

    Every level is within the 5% regression budget (worst: c=4, -2.8% throughput, +3.9% p50). The v2 c=16 run had a noisy tail (p95 2873 ms).

    Notes on the ROCm v2 run¶

    • 100 requests per level; avg server batch 1.0 at c=1 and ~7.8 at c=16. Concurrency 8: 8.2 req/s.
    • Compute-bound: GEMMs ~83% of GPU kernel time at ~95 TFLOPS. Batching adds ~30% throughput, not more.
    • A ~330-token single forward is GPU-bound: kernel/wall 0.78 measured without the profiler (68.4 / 87.6 ms, 2026-10-18, MASK_FREE + FAST_HEAD + TunableOp). The earlier "about half is host overhead" came from wall time measured inside the profiler. With attention_mask=None the backbone captures into a HIP graph (transformers skips its mask check while capturing); replay saves ~27% at 64 tokens, ~5% at 128 and nothing at 384. Replay parity is not checked yet.
    • The joint head is ~5% of the forward. Padding to a multiple of 64 beat raw lengths and full buckets (CLEF_PAD_MULTIPLE); re-measure on other backends before assuming the same.
    • Warm restart: load ~45-100 s, warmup ~12 s with a warm Triton cache (~110 s the very first time).

    Quantization accuracy (CUDA only)¶

    Measured on the RTX 4070 Ti (12 GB) against the lossless offload run (OFFLOAD=cpu CLEF_MAX_DEVICE_MEMORY_GB=10), not against plain bf16, because bf16 does not fit in 12 GB. Offload is documented to give identical probabilities to bf16 (0 / 0 on ROCm); that was not re-checked on CUDA.

    Mode Max abs prob diff Mean abs diff Argmax agreement Latency vs reference
    int8, torchao (CLEF_QUANT_BACKEND=torchao) 0.066 0.0057 396 / 399 (99.2%) p50 170 ms vs 572 ms
    int8, bitsandbytes (CUDA default) 0.209 0.0172 377 / 399 (94.5%) p50 232 ms vs 572 ms
    nf4 (bitsandbytes) 0.444 0.0333 363 / 399 (91.0%) p50 153 ms vs 572 ms

    The numbers match the ROCm run of the same two backends (torchao 0.0058 / 2 flips, bitsandbytes 0.0175 / 22 flips). nf4 also matches ROCm (0.0329 / 35 flips) and stays not recommended. Plain bf16 needs a 24 GB card and was not run.

    • The cap is enforced on the PyTorch allocator. The whole process (reserved memory + driver context) measured about 0.65 GB above the cap, so use N - 0.5 GB for an N GB card: 15 for 16 GB, 11 for 12 GB, 7 for 8 GB.
    • Host RAM after load is the process RSS once the model is in place: the pinned copies of everything that was moved off the GPU. During loading RSS peaks higher (up to ~19 GB) because the safetensors files are memory-mapped; those pages are reclaimable page cache.
    • p95 is dominated by the longest records of the eval set (~1500 tokens), which are compute-bound and unaffected by the settings; p50 is the number that moves.
    • Offload latency is the PCIe copy of the streamed layers (about 0.43 GB per layer at ~26 GB/s) partly hidden behind compute; batching amortises it (req/s at c=8 falls less than single latency rises).
    • int8 flips: 2 of 399 questions changed their top option, against 0 for fp16 vs bf16. The mean probability error 0.006 is ~3x the fp16/bf16 noise floor.

    Background: docs/memory.md. Reproduce with bench/memory_bench.py. CUDA and Apple Silicon rows are still pending hardware.

    • On CUDA, bitsandbytes is the auto choice for int8, and it is the worse one here: 3x the error, 7x the flipped answers and 36% slower than torchao. See the note in memory.md.
    • The lossless modes need more host RAM than a default 15 GB WSL2: OFFLOAD=cpu was refused at caps of 10 and 11 GB ("11.0 GB of weights stay in host memory, 13.0 GB free"), and the cap 10 run peaked at 17.1 GB of RSS while loading.
    • causal-conv1d 1.7.0, built from source (the cuda-fast extra, ~23 min): clef doctor no longer warns about the fast path. memory_bench int8 torchao + offload went from p50 170.3 / p95 488.7 ms and 5.03 req/s to 167.5 / 481.2 ms and 5.11 req/s (about 1.6%, inside the ~5% same-day drift), parity unchanged (mean 0.0054, 2 of 399 flips), and the integration tests still pass (22). clef bench: c=1 6.2 req/s, p50 161 ms; c=16 8.9 req/s.
    • Not run: plain bf16 (needs 24 GB) and native Ubuntu.

    CLEF_PAD_MULTIPLE on CUDA (RTX 4070 Ti, int8 torchao + offload, 2026-10-12)¶

    The default of 64 was chosen on ROCm. clef bench --requests 100 --concurrency 1,8, ~330-token records, a fresh server per run; the default (64) was measured twice and a multiple of 8 three times.

    CLEF_PAD_MULTIPLE c=1 req/s, p50 c=8 req/s, p50
    8 6.0, 165.5 / 166.5 / 166.1 ms 9.5, 880 / 866 / 869 ms
    64 (default) 5.9, 169.3 / 168.9 ms 8.5, 942 / 949 ms
    128 5.9, 169.6 ms 8.5, 956 ms

    A multiple of 8 was about 12% faster at concurrency 8 and 2% faster at concurrency 1, consistently across the three runs. Only one mode and one record length were measured; the bf16 and mixed-length workloads are untested, so the default is unchanged.

    Speed flags and TunableOp on ROCm (RX 7900 XTX, 2026-10-18)¶

    bench/perf_check.sh, one session, result cache off, fixed-length records (clef bench). Parity is against the flags-off engine (200 records, 10 with images; the flags-off engine run twice differs by 0.0, so the 2e-3 gate is the floor). Every top-1 change was a near coin-flip (reference top-2 margin 0.0015-0.017, the lowest 1.5% of the 399 questions).

    Variant Parity: max |dp| / top-1 flips c=1 p50 / p95 ms c=1 req/s c=8 req/s c=16 req/s
    flags off (base) reference 133.8 / 683.7 4.5 8.5 9.1
    CLEF_MASK_FREE=1 0.0235 / 1 137.5 / 610.0 4.5 8.6 9.0
    CLEF_FAST_HEAD=1 0.0038 / 0 133.3 / 588.8 4.6 8.6 9.5
    both 0.0235 / 1 133.8 / 585.6 4.6 8.7 9.5
    CLEF_TUNABLEOP=1 (tuned) 0.0219 / 3 104.2 / 502.5 5.7 10.1 10.8
    both + TunableOp (the ROCm default) 0.0273 / 0 98.6 / 452.3 6.0 11.3 11.8

    Step 0 (profile_forward.py --batch 8): single record kernel/wall 0.22 with profiler overhead in the wall time (0.78 without it, see above), batch 8 0.68; GEMM 81-84% of kernel time. Accuracy on the 47 labelled tickets: 0.872 with TunableOp off and on.

    Mixed-length traffic (clef bench --mixed), TunableOp off vs on: c=1 5.9 vs 7.6 req/s (p50/p95/max 151/241/249 vs 111/199/204 ms), c=8 6.0 vs 7.9, c=16 6.2 vs 7.9 (+27-32%).

    TunableOp cost and design. On gfx1100 PyTorch already uses rocBLAS; TunableOp's gain is choosing better rocBLAS solutions (1054 of 1181 tuned GEMMs are rocBLAS, 66 hipBLASLt; tuned GEMMs ~40% faster than rocBLAS's own pick). Tuning costs a fixed ~4-8 s per GEMM whatever the per-candidate budget (30 ms / 100 runs, 5 ms / 20 and 1 ms / 3 pick equally fast kernels), so the ~535 GEMMs of the serving grid take about an hour. Tuning on the request instead (the old behaviour) gave single requests p50 2.7 s, p95 39 s until every shape had been seen. clef now tunes in the background while idle (a step only after 2 s without requests), never on a live request.
